> ステータス: 案（レビュー担当: [@taitai03](https://github.com/taitai03)）

> 前提: [requirements.md](requirements.md)、[architecture.md](architecture.md)

## 0. 全体像

### ゴール

**業務で、仕様を渡されたら自分でコードを書ける状態になること。** プログラミングの勉強のためのプログラミングにはしない。文法は目的ではなく、業務の課題を解くための道具として、必要になったところで教える。

### カリキュラムの方針

1. **題材はすべて業務**
   全コースで、架空のECショップ「さくらマート」の業務を題材にする。商品、注文、在庫、会員、社内の管理画面など、現場でよく扱うデータと処理を使う。「自己紹介を表示する」「じゃんけんゲーム」のような、業務につながらない題材は使わない。

2. **課題は業務のチケット形式**
   課題文は、実際の開発と同じく「背景・やること・受け入れ条件」で書く（[5. 課題の書き方](#5-課題の書き方)）。何のために書くコードかを常に意識させる。

3. **足場を段階的に外す**
   最終的に「白紙から自分で書ける」ようにするため、与えるものを少しずつ減らす。

   | 段階 | 与えるもの | 受講者がやること |
   | --- | --- | --- |
   | 初級前半 | ほぼ完成したコード | 穴埋め、壊れたコードの修正 |
   | 初級後半 | 関数の名前と仕様 | 関数の中身を白紙から書く |
   | 中級 | チケットと既存のアプリ | 既存のコードを読み、機能追加やバグ修正をする |
   | 各レベルの総まとめ | 仕様書だけ | 構成から自分で考えて作る |
   | 上級 | 問題を抱えた既存のコードベース | 問題を見つけ、設計の判断をして直す |

4. **現場で必要な「書く以外」のスキルも教える**
   エラーメッセージの読み方、デバッグ、公式ドキュメントの調べ方、既存コードの読み方、PRの説明の書き方、AIツールとの付き合い方。これらは独立したレッスンにするだけでなく、各レッスンの中でも繰り返し使わせる。

5. **既存のコードを触る機会を多くする**
   実務では、白紙から書くより既存のコードを読んで変更する時間のほうが長い。中級以降は、用意した「さくらマート」のアプリに対して機能追加やバグ修正をする課題を中心にする。

### コースとレッスン数

| コース | 初級 | 中級 | 上級 |
| --- | --- | --- | --- |
| JavaScript / TypeScript | 8本（ブラウザ） | 10本（PR） | 10本（PR＋AIレビュー） |
| Ruby / Rails | 8本（ブラウザ） | 9本（PR） | 8本（PR＋AIレビュー） |
| Swift | 8本（Playground＋クイズ） | 9本（PR） | 8本（PR＋AIレビュー） |
| 共通: 開発の準備 | 5本（初級と中級の間） | | |

合計 83本。各レッスンは「短い解説 → 演習 → 確認クイズ（3問程度）」で、1本30〜60分を想定する。

### 上級の演習の種類

- 改善: 問題のあるコードを、テストを通したままリファクタリングする
- 脆弱性: 脆弱性を含むコードを直す。攻撃を再現するテストで判定する
- 設計: 仕様から機能を追加し、設計方針をPRの説明に書く
- 運用: 本番環境で動かすことを前提にした変更をする
- レビュー: 用意されたPRをレビューして指摘を書く

### 表の見方

- **学ぶこと**: レッスンで扱う内容
- **演習（チケット）**: 手を動かす課題。業務のチケットとして出す
- **判定**: 自動テスト（テスト）、確認クイズ（クイズ）、AIレビュー（AI）のどれで判定するか

## 5. 課題の書き方

中級以降の課題は、GitHubのIssueや業務のチケットと同じ形で書く。受講者は課題文を読んで、何を作るか・どこまでやれば終わりかを自分で判断する。

```markdown
## 背景
管理画面の注文一覧で、特定の期間の注文だけを見たいという要望がCSチームから来ています。

## やること
- 注文一覧API（`GET /api/orders`）に、期間（`from` / `to`）とステータスで絞り込む機能を追加する

## 受け入れ条件
- [ ] `from` と `to` を指定すると、その期間に作成された注文だけが返る
- [ ] `status` を指定すると、そのステータスの注文だけが返る
- [ ] 日付の形式が正しくない場合は 400 を返す
- [ ] 既存のテストがすべて通る

## 参考
- Drizzle のドキュメント: where 句の書き方
```

- 総まとめの課題では、「やること」を細かく書かず、仕様書だけを渡す
- ただし自動テストで判定するため、関数名、APIのパス、画面の要素など、テストが依存するインターフェースは仕様書に明記する
- 受け入れ条件は、同梱するテストと1対1で対応させる

## 6. 決定事項

- Railsのテストは **RSpec** を使う（現場で使われることが多いため）
- JS/TSでAPIを作るときは **Next.js の Route Handlers** を使う。画面とAPIを同じフレームワークで学べる
- JS/TSコースで **React / Next.js を扱う**
- 画面の判定: コンポーネントは React Testing Library でテストし、見た目や構成はAIレビューで確認する
- 教材のレビュー担当は全言語 [@taitai03](https://github.com/taitai03)（`CODEOWNERS` に登録済み）
- 全コースで **業務を題材にする**。架空のECショップ「さくらマート」を共通の題材にし、中級以降は既存のアプリに対する機能追加・バグ修正を中心にする（アプリの仕様は [sakura-mart.md](sakura-mart.md)）
- 初級の演習の料金計算なども、[さくらマートの業務仕様](sakura-mart.md#3-業務仕様3言語で共通) に合わせる
