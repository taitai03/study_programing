## まず「再現」する

バグの報告を受けたら、コードを読み始める前に **手元で同じ現象を起こせるか** を確かめます。

1. 報告を整理する（どの画面の、どの数字が、どう違うのか。期待していた値は何か）
2. 同じ条件を手元で作る（キャンセルの注文がある月、など）
3. **再現する手順を、テストとして書く**（失敗することを確かめる）

```ruby
it "今月の売上に、キャンセルの注文を含めない" do
  create(:order, total: 1000, ordered_at: now - 1.hour)
  create(:order, total: 9999, ordered_at: now - 3.days, status: "cancelled")
  expect(SalesSummary.new(now:).this_month).to eq(sales: 1000, count: 1)
end
```

## 知らないコードの読み方

全部を頭から読む必要はありません。**画面の入口から、データの流れを追います**。

1. **入口を見つける**: `bin/rails routes` や、サーバーのログの `Processing by Admin::DashboardController#show` から、コントローラーのアクションを探す
2. **呼び出しをたどる**: アクション → 使っているモデルのメソッド → スコープ、と定義を順に読む（エディタの「定義へ移動」）
3. **似ている箇所を比べる**: 「今日の売上は正しいのに、今月の売上は違う」なら、2つの処理の **違い** に原因がある
4. **テストを読む**: 何が確かめられていて、何が確かめられていないか
5. **履歴を見る**: `git log -p app/models/sales_summary.rb` や `git blame` で、その行が **いつ、なぜ** 変わったか

コメントやメソッド名は参考になりますが、**名前どおりに動くとは限りません**。動きが事実です。

## 原因を絞り込む

### rails console で試す

```ruby
now = Time.zone.parse("2026-04-15 12:00")
SalesSummary.new(now:).this_month
Order.where(ordered_at: now.all_month).group(:status).count   # ステータスごとの件数
```

### ログで SQL を見る

開発用サーバーのログ（`log/development.log`）には、実行された SQL が出ます。**WHERE の条件に `status != 'cancelled'` が入っているか** を見れば、キャンセルを除いているかが分かります。console でも、`Order.for_sales.to_sql` で SQL を確かめられます。

### debug gem で止める

止めたい行に `debugger` と書いてテスト（またはサーバー）を実行すると、その行で止まり、変数の中身を見たり、1行ずつ進めたりできます。

```ruby
def this_month
  debugger
  summarize(...)
end
```

| コマンド | 内容 |
| --- | --- |
| `p 式` / `pp 式` | 値を表示する |
| `next` / `n` | 次の行へ |
| `step` / `s` | 呼んでいるメソッドの中に入る |
| `continue` / `c` | 次に止まるところまで進める |
| `info` | いまの変数の一覧 |

調べ終わったら `debugger` の行は必ず消してから commit します。

## 直し方: 原因を直す

「今月の売上からキャンセルの金額を引く」のような、つじつま合わせの直し方をしてはいけません。**なぜキャンセルが含まれたのか（原因）** を突き止めて、そこを直します。

- 同じ原因で、ほかにも影響している場所がないかを調べる（ほかの集計も同じスコープを使っていないか）
- 業務のルール（「売上にはキャンセルを含めない」）は、**名前の付いたスコープ** にまとめて、どこからでもそれを使う
- 再現のテストを、**再発防止のテスト** として残す
- PRの説明に「原因」「直し方」「影響の範囲」を書く
