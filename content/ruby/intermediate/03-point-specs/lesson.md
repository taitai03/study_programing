## なぜテストを書くのか

テストは「このコードは仕様どおりに動く」ことを、**何度でも、自動で、すぐに** 確かめるためのコードです。

- 自分の変更で、ほかの機能を壊していないかがすぐ分かる
- 「どう動くべきか」がテストとして残るので、仕様のドキュメントにもなる
- バグを直すときに、先に「バグを再現するテスト」を書くと、直ったことを確かめられ、再発も防げる

## RSpec の基本

```ruby
require "rails_helper"

RSpec.describe PointCalculator do
  describe ".points" do
    context "ゴールド会員のとき" do
      it "2%のポイントを付ける" do
        expect(described_class.points(10_000, "gold")).to eq(200)
      end
    end
  end
end
```

| 書き方 | 意味 |
| --- | --- |
| `describe` | テストの対象（クラス、メソッド）。`.points` はクラスメソッド、`#name` はインスタンスメソッドを表す習慣 |
| `context` | 条件（「〜のとき」） |
| `it` | 1つのテスト（「〜する」） |
| `expect(実際の値).to eq(期待する値)` | 値が同じかを確かめる |
| `expect { ... }.to raise_error(クラス)` | 例外が起きるかを確かめる（ブロックで渡す） |
| `described_class` | `describe` に書いたクラス |

```bash
bundle exec rspec spec/models/point_calculator_spec.rb   # このファイルだけ
bundle exec rspec spec/models/point_calculator_spec.rb:12 # 12行目のテストだけ
bundle exec rspec                                        # すべて
```

テストのファイルは `spec/` の下に、`app/` と同じ構成で `〇〇_spec.rb` という名前で置きます。

### テストデータの準備

DBを使うテストでは、**FactoryBot** でデータを作ります（`spec/factories/`）。必要な項目だけを指定し、残りは決まった値になります。

```ruby
let(:member) { create(:member, rank: "gold") }   # DBに保存する
let(:product) { build(:product, stock: 0) }      # 保存しない（速い）
```

## テストケースの考え方

思いついた例を1つ書くだけでは、バグは見つかりません。次の3つの観点で、**仕様からケースを洗い出します**。

| 観点 | 内容 | ポイント計算の例 |
| --- | --- | --- |
| 正常系 | 仕様どおりの普通の入力 | 一般は1%、ゴールドは2% |
| 境界値 | 結果が切り替わる境目と、その前後 | 端数（1,250円 → 12.5 → 12）、1ポイントに満たない金額 |
| 異常系 | ありえない・想定外の入力 | 0円、マイナスの金額 |

バグの多くは **境目** にあります。「端数は切り捨て」の仕様に対して、`1,000円 → 10` だけをテストしても、四捨五入で書いたバグは見つかりません。小数がちょうど .5 や .9 になる値を選びます。

## 「テストのテスト」

書いたテストが本当にバグを見つけられるかは、**わざとバグを入れて、テストが失敗するか** で確かめられます（ミューテーションテストと呼ばれる考え方です）。この課題では、PRのチェックで、いくつかのバグを入れたポイント計算にあなたのテストを当てて、すべて見つけられるかを確かめます。

## テストを書いてから直す

1. 仕様（またはバグの報告）から、**期待する動き** をテストに書く
2. テストを実行して、**失敗することを確かめる**（バグを再現できた）
3. コードを直す
4. テストが通ることを確かめる
