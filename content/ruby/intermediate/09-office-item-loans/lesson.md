## 総まとめの進め方

この課題では、「どのファイルに何を書くか」は細かく指示しません。**仕様書から、自分で作業を分解して進めます**。

### 1. 仕様を読んで、モデルを考える

まず、仕様に出てくる「もの」と「出来事」を洗い出し、テーブルを考えます。

| 仕様の言葉 | モデル | 主な列 |
| --- | --- | --- |
| 備品 | `OfficeItem` | 名前、管理番号 |
| 貸出（いつ、誰に、いつまで） | `Loan` | 備品、借りた人、返却予定日、返却した日時 |

「貸出中かどうか」を備品の列（`status` など）に持たせる設計もありますが、**貸出の記録から分かることは、なるべく二重に持たない** ほうが食い違いが起きません。「返却されていない貸出があれば貸出中」と考えます。

### 2. ルールをどこで守るかを決める

| ルール | 守る場所 |
| --- | --- |
| 管理番号は重複しない | バリデーション＋一意のインデックス |
| 返却予定日は今日から30日後まで | `Loan` のバリデーション（**貸し出すときだけ**） |
| 貸出中の備品は貸し出せない | `Loan` のバリデーション（貸し出すときだけ） |
| 期限切れの判定 | `Loan#overdue?` と scope |

`validate :メソッド名, on: :create` のように書くと、**作るときだけ** 確かめるバリデーションになります。期限を過ぎた貸出を返却するとき（更新するとき）に、「返却予定日は今日以降」のチェックで失敗しないようにするためです。

### 3. 下の層から作る

1. マイグレーションとモデル（バリデーション、scope、メソッド）→ モデルのテスト
2. ルーティングとコントローラー → リクエストのテスト
3. ビュー → 画面で確認

1つできるたびに commit すると、問題が起きたときに戻りやすくなります。

## 日付の扱い

- 「今日」は `Date.current`（`config.time_zone` の日付）を使う。`Date.today` はサーバーのタイムゾーンになるので、ずれることがある
- テストで「今日」を固定するには `travel_to` を使う（`ActiveSupport::Testing::TimeHelpers`）

```ruby
travel_to(Time.zone.parse("2026-04-15 10:00")) do
  expect(loan.overdue?).to be(true)
end
```

## 入れ子のルーティング

「この備品を貸し出す」のように、親（備品）に属する操作は、ルーティングを入れ子にすると URL から親が分かります。

```ruby
resources :office_items, only: %i[index new create] do
  resources :loans, only: %i[create]   # POST /admin/office_items/:office_item_id/loans
end
```

## PRの説明を書く

総まとめの課題は、変更が大きくなります。レビューする人のために、PRの説明に次を書きましょう。

- 何を作ったか（仕様書のどこに対応するか）
- 設計で判断したこと（テーブルの設計、ルールをどこで守っているか、なぜそうしたか）
- 確かめたこと（テスト、画面での確認）
- 対象外にしたこと、気になっていること
