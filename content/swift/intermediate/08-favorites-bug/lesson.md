## まず「再現」する

バグの報告を受けたら、コードを読み始める前に **同じ現象を起こせるか** を確かめます。

1. 報告を整理する（何をしたら、何が起きたか。全部消えるのか、一部が消えるのか）
2. シミュレーターで同じ操作をする（お気に入りに入れる → アプリを終了して起動し直す）
3. **再現する手順を、テストとして書く**

「アプリの再起動」は、テストでは **同じ保存先から、もう一度オブジェクトを作る** ことで再現できます。保存先をプロトコル（`KeyValueStore`）にしてあるので、テストではメモリ上の保存先を使えます。

```swift
let storage = InMemoryKeyValueStore()
FavoritesStore(store: storage).toggle(42)
#expect(FavoritesStore(store: storage).isFavorite(42))   // 再起動しても残っているか
```

## 知らないコードの読み方

1. **入口を見つける**: 画面の「♡」ボタン（`ProductDetailView`）から、呼んでいるメソッドをたどる
2. **データの流れを追う**: お気に入りが「どこに保存され」「いつ保存され」「どこから読まれるか」を確かめる
3. **報告と照らし合わせる**: 「全部消える」なら保存か読み込みが動いていない、「一部（最後のもの）が消える」なら保存の **タイミング** があやしい
4. **履歴を見る**: `git log -p ファイル名` で、最近の変更を確かめる。「いつから起きたか」と変更の時期が合えば、手がかりになる

## 原因を絞り込む

### ブレークポイント

Xcode で行番号をクリックすると、**ブレークポイント** を置けます。アプリを実行してその行に来ると止まり、変数の中身を見られます。

| 操作 | 内容 |
| --- | --- |
| Step Over（F6） | 次の行へ |
| Step Into（F7） | 呼んでいるメソッドの中へ |
| 変数ビュー | いまの変数の値 |
| `po 式`（デバッグコンソール） | 式の値を表示する |

テスト（`SakuraMartKit`）にもブレークポイントを置けます。Xcode で `Package.swift` を開き、テストの横の ◇ で実行します。

### ログ

止めずに流れを見たいときは、`print` やロガーで値を出します。「保存する直前の値」と「保存したあとの値」を出すと、タイミングのずれが分かります。調べ終わったらログは消します。

## 直し方: 原因を直す

- 「再起動のときに、最後の1件を足し直す」のような **つじつま合わせ** はしない。なぜ最後の1件が保存されないのか（原因）を直す
- 状態を変える処理と、保存する処理の **順番** は、バグが起きやすいところ。「変えてから保存する」がいつも成り立つ書き方にする
- 再現のテストを、**再発防止のテスト** として残す
- PRの説明に「原因」「直し方」「影響の範囲」を書く
