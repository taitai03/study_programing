## なぜテストを書くのか

テストは「このコードは仕様どおりに動く」ことを、**何度でも、自動で、すぐに** 確かめるためのコードです。

- 自分の変更で、ほかの機能を壊していないかがすぐ分かる
- 「どう動くべきか」がテストとして残るので、仕様のドキュメントにもなる
- バグを直すときに、先に「バグを再現するテスト」を書くと、直ったことを確かめられ、再発も防げる

## Swift Testing の基本

```swift
import Testing
@testable import SakuraMartKit

@Suite("ポイント計算")
struct PointCalculatorTests {
    @Test("ゴールド会員は2%")
    func gold() {
        #expect(PointCalculator.points(taxIncluded: 10_000, rank: .gold) == 200)
    }
}
```

| 書き方 | 意味 |
| --- | --- |
| `@Suite("名前") struct` | テストのまとまり |
| `@Test("〜のとき〜になる") func` | 1つのテスト。名前に「条件と期待する結果」を書く |
| `#expect(式)` | 式が `true` かを確かめる。失敗すると、式の中の値も表示される |
| `#require(式)` | `#expect` と同じだが、失敗したらそのテストを止める（オプショナルを外すときなど） |
| `@testable import` | `internal` のものもテストから使えるようにする |

### 引数付きのテスト

同じ確かめ方を、値を変えて何度も行うときは、`arguments:` を使います。1つ1つが別のテストとして実行・表示されます。

```swift
@Test("端数は切り捨てる", arguments: [(1250, 12), (1299, 12), (1201, 12)])
func floor(amount: Int, expected: Int) {
    #expect(PointCalculator.points(taxIncluded: amount, rank: .regular) == expected)
}
```

```bash
swift test --package-path SakuraMartKit                              # すべて
swift test --package-path SakuraMartKit --filter PointCalculatorTests # 一部だけ
```

Xcode では、`SakuraMartKit/Package.swift` を開いて Cmd + U、またはテストの横の ◇ を押して実行できます。

## テストケースの考え方

思いついた例を1つ書くだけでは、バグは見つかりません。次の3つの観点で、**仕様からケースを洗い出します**。

| 観点 | 内容 | ポイント計算の例 |
| --- | --- | --- |
| 正常系 | 仕様どおりの普通の入力 | 一般・シルバーは1%、ゴールドは2% |
| 境界値 | 結果が切り替わる境目と、その前後 | 端数（1,250円 → 12.5 → 12）、1ポイントに満たない金額 |
| 異常系 | ありえない・想定外の入力 | 0円、マイナスの金額 |

バグの多くは **境目** にあります。「端数は切り捨て」の仕様に対して、`10,000円 → 100` だけをテストしても、四捨五入で書いたバグは見つかりません。小数がちょうど .5 や .9 になる値を選びます。

## 「テストのテスト」

書いたテストが本当にバグを見つけられるかは、**わざとバグを入れて、テストが失敗するか** で確かめられます（ミューテーションテストと呼ばれる考え方です）。この課題では、PRのチェックで、いくつかのバグを入れたポイント計算にあなたのテストを当てて、すべて見つけられるかを確かめます。

## テストを書いてから直す

1. 仕様（またはバグの報告）から、**期待する動き** をテストに書く
2. テストを実行して、**失敗することを確かめる**（バグを再現できた）
3. コードを直す
4. テストが通ることを確かめる
