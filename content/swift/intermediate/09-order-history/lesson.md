## 総まとめの進め方

この課題では、「どのファイルに何を書くか」は細かく指示しません。**仕様書から、自分で作業を分解して進めます**。

### 1. 画面の状態を洗い出す

通信してデータを表示する画面には、少なくとも次の状態があります。**すべての状態で何を表示するか** を、作る前に決めます。

| 状態 | 表示 |
| --- | --- |
| 読み込み中 | 「読み込み中…」 |
| 読み込めた（1件以上） | 一覧 |
| 読み込めた（0件） | 「注文はまだありません」 |
| 失敗 | 理由と「もう一度読み込む」ボタン |

0件と失敗は、ユーザーにとって意味がまったく違います（「注文していない」と「見られない」）。同じ表示にしてはいけません。

このアプリには、状態を表す `LoadState`（`idle` / `loading` / `loaded` / `failed`）があります。商品一覧の ViewModel（`ProductListViewModel`）と画面が、そのまま参考になります。

### 2. ロジックと画面を分ける

| どこに | 何を |
| --- | --- |
| ViewModel（`SakuraMartKit`） | 読み込み、状態の管理、並べ替え、月ごとのまとめ、表示用の文字列 | 
| View（`SakuraMart`） | ViewModel の値の表示、操作の受け渡し |

「月ごとにまとめる」「日時を `2026/04/15 12:00` の形にする」のような処理も、ViewModel に書くとテストできます。日付は **日本時間のカレンダー**（`Calendar.japan`）で扱います。

### 3. 下の層から作る

1. ViewModel を作り、テストを書く（偽物の API を使って、成功・0件・失敗を確かめる）
2. 画面を作り、シミュレーターで確かめる（モックの API の遅延で「読み込み中」も見える）
3. タブに追加する

1つできるたびに commit すると、問題が起きたときに戻りやすくなります。

## 偽物の API でテストする

`OrderAPI` はプロトコルなので、テストでは結果を自由に決められる偽物を渡せます。「失敗したあと、もう一度読み込むと表示できる」のように **途中で結果を変えたい** ときは、actor にして結果を差し替えられるようにします。

```swift
private actor FakeOrderAPI: OrderAPI {
    var result: Result<[PastOrder], APIError>
    func set(_ result: Result<[PastOrder], APIError>) { self.result = result }
    func fetchOrders() async throws -> [PastOrder] { try result.get() }
    ...
}
```

## PRの説明を書く

総まとめの課題は、変更が大きくなります。レビューする人のために、PRの説明に次を書きましょう。

- 何を作ったか（仕様書のどこに対応するか）
- 設計で判断したこと（ViewModel と View の分け方、状態の扱い）
- 確かめたこと（テスト、シミュレーターでの確認。画面のスクリーンショットがあると分かりやすい）
- 対象外にしたこと、気になっていること
