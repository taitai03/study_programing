## まず「再現」する

バグの報告を受けたら、コードを読み始める前に **手元で同じ現象を起こせるか** を確かめます。再現できれば、直したかどうかも同じ手順で確かめられます。

1. 報告の内容を整理する（いつ、誰が、何をしたら、何が起きた。期待していた結果は何か）
2. 同じ条件を手元で作る（同じ会員ランク、同じクーポン、同じ商品）
3. **再現する手順を、テストとして書く**（失敗することを確かめる）

```ts
it("クーポンの割引は1回だけ適用される", () => {
  const order = createOrder(db, { memberId: 1, items: [{ productId: 1, quantity: 2 }], couponCode: "WELCOME500" });
  expect(order.total).toBe(order.subtotal - order.rankDiscount - order.couponDiscount + order.tax + order.shippingFee);
});
```

## 知らないコードの読み方

全部を頭から読む必要はありません。**入口から、データの流れを追います**。

1. **入口を見つける**: 画面ならページのファイル、APIなら `route.ts`。URL からファイルを探す
2. **呼び出しをたどる**: エディタの「定義へ移動」（F12 / Cmd+クリック）で、呼んでいる関数へ移動する。「参照を検索」（Shift+F12）で、その関数がどこから呼ばれているかを調べる
3. **データの形を確かめる**: 型の定義（`type`、`interface`、DBのスキーマ）を見て、どんな値が流れているかを知る
4. **テストを読む**: テストは「この関数がどう動くべきか」の説明書になっている
5. **履歴を見る**: `git log -p ファイル名` や `git blame` で、**いつ、なぜ** その行が書かれたか（コミットのメッセージ、チケット番号）を調べる

コメントは参考になりますが、**コメントが正しいとは限りません**。コメントと実際の動きが違う場合は、動きのほうが事実です。

## 原因を絞り込む

### ログ（console.log）

疑わしい場所の前後で値を出力して、**どこで期待と違う値になったか** を探します。

```ts
console.log("pricing", pricing); // ここまでは正しい？
```

調べ終わったら、ログは消してから commit します。

### デバッガ

VS Code では、行番号の左をクリックして **ブレークポイント** を置き、デバッグ実行すると、その行で止まって変数の中身を見られます。Vitest のテストも、VS Code の「JavaScript Debug Terminal」で `npx vitest run ファイル名` を実行すると、ブレークポイントで止まります。

| 操作 | 内容 |
| --- | --- |
| ステップオーバー | 次の行へ進む |
| ステップイン | 呼んでいる関数の中に入る |
| 変数・ウォッチ | 変数や式の、いまの値を見る |

### 二分探索

処理の流れのちょうど真ん中で値を確かめ、正しければ後半、間違っていれば前半に原因がある、と範囲を半分ずつ狭めます。いつから起きたかが分かっている場合は、`git bisect` でコミットを二分探索することもできます。

## 直し方: 原因を直す

「合計が500円安すぎる」からといって、最後に500円足すような直し方（つじつま合わせ）をしてはいけません。**なぜそうなったのか（原因）** を突き止めて、原因の場所を直します。つじつま合わせは、別の条件で新しいバグになります。

直したら:

- 再現のテストが通ることを確かめる（**再発防止のテスト** として残す）
- 同じ原因で、ほかにも影響している場所がないかを調べる
- PRの説明に「原因」「直し方」「影響の範囲」を書く。レビューする人や、将来この行を読む人の助けになる
