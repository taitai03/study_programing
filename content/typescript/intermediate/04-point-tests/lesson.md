## なぜテストを書くのか

テストは「このコードは仕様どおりに動く」ことを、**何度でも、自動で、すぐに** 確かめるためのコードです。

- 自分の変更で、ほかの機能を壊していないかがすぐ分かる（リファクタリングや機能追加が怖くなくなる）
- 「どう動くべきか」がテストとして残るので、仕様のドキュメントにもなる
- バグを直すときに、先に「バグを再現するテスト」を書くと、直ったことを確かめられ、同じバグの再発も防げる

## Vitest の基本

```ts
import { calculatePoints } from "./points";

describe("calculatePoints", () => {
  it("一般会員は1%", () => {
    expect(calculatePoints(10000, "regular")).toBe(100);
  });
});
```

| 書き方 | 意味 |
| --- | --- |
| `describe("名前", () => { ... })` | テストをまとめるグループ |
| `it("〜のとき〜になる", () => { ... })` | 1つのテスト。名前は「条件と期待する結果」を書く |
| `expect(実際の値).toBe(期待する値)` | 値が同じかを確かめる |
| `toEqual` | オブジェクトや配列の中身が同じか |
| `toThrow("メッセージ")` | 例外が投げられるか（`expect(() => f()).toThrow()` と関数で包む） |

```bash
npx vitest src/lib/points.test.ts   # このファイルだけ。保存するたびに再実行される
npm test                            # すべてのテストを1回実行する
```

テストのファイルは、テストするファイルと同じ場所に `〇〇.test.ts` という名前で置きます。

## テストケースの考え方

思いついた例を1つ書くだけでは、バグは見つかりません。次の3つの観点で、**仕様からケースを洗い出します**。

| 観点 | 内容 | ポイント計算の例 |
| --- | --- | --- |
| 正常系 | 仕様どおりの普通の入力 | 一般は1%、ゴールドは2% |
| 境界値 | 結果が切り替わる境目と、その前後 | 端数（1,250円 → 12.5 → 12）、1ポイントに満たない金額 |
| 異常系 | ありえない・想定外の入力 | 0円、マイナスの金額 |

### 境界値が大事な理由

バグの多くは「境目」にあります。`>` と `>=` の間違い、四捨五入と切り捨ての間違いなどです。たとえば「端数は切り捨て」の仕様に対して、`1,000円 → 10` だけをテストしても、四捨五入で書いたバグは見つかりません。**端数がちょうど .5 になる値** や **.9 になる値** を選びます。

### 1つのテストでは1つのことを確かめる

1つの `it` にいろいろ詰め込むと、失敗したときに何が悪いのか分かりにくくなります。名前を読むだけで「どんな仕様を確かめているか」が分かるようにします。

## 「テストのテスト」

書いたテストが本当にバグを見つけられるかは、**わざとバグを入れて、テストが失敗するか** で確かめられます（ミューテーションテストと呼ばれる考え方です）。この課題では、PRのチェックで、いくつかのバグを入れたポイント計算にあなたのテストを当てて、すべて見つけられるかを確かめます。

## テストを書いてから直す

バグを直すときの手順です。

1. 仕様（またはバグの報告）から、**期待する動き** をテストに書く
2. テストを実行して、**失敗することを確かめる**（バグを再現できた）
3. コードを直す
4. テストが通ることを確かめる

先にコードを直してしまうと、テストが「本当にバグを見つけられるか」を確かめられません。
