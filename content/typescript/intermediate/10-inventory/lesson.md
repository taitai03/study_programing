## 総まとめの進め方

この課題では、「どのファイルに何を書くか」は細かく指示しません。**仕様書から、自分で作業を分解して進めます**。現場で機能を追加するときと同じ流れです。

### 1. 仕様を読んで、分からないことをなくす

- 誰が、どんな場面で使う機能か
- 決まっているインターフェース（関数名、画面の文言、DBの列）はどれか
- 書かれていないこと（例: 注文がキャンセルされたら在庫を戻すか）は、**勝手に決めずに確認する**。この課題では、仕様書の「対象外」に書いてあります

### 2. 変更する場所を洗い出す

既存のコードを読んで、影響する場所をリストにします。在庫管理なら、たとえば次のような場所です。

| 層 | 変更 |
| --- | --- |
| DB | 商品に在庫数の列を追加する（マイグレーション） |
| 初期データ | 在庫の初期値 |
| 業務ロジック | 在庫の一覧、入荷、在庫不足の判定。**注文したときに在庫を減らす** |
| 画面 | 在庫の一覧と入荷のフォーム、ナビゲーション、ダッシュボードのアラート |
| テスト | それぞれの動きを確かめる |

「注文したら在庫が減る」のように、**既存の機能に影響する変更** を見落とさないことが大事です。

### 3. 小さく作って、こまめに確かめる

下の層（DB、業務ロジック）から作り、テストで確かめてから、上の層（画面）に進みます。1つできるたびに commit すると、問題が起きたときに戻りやすくなります。

## DBの列を追加する

```ts
// src/db/schema.ts
stock: integer("stock").notNull().default(0),
```

```bash
npm run db:generate   # drizzle/ にマイグレーションのSQLができる
npm run db:reset      # 手元のDBを作り直して、初期データを入れ直す
```

テスト用のDBも、`drizzle/` のマイグレーションから作られます。**マイグレーションのファイルを commit し忘れると、ほかの人やCIでは列がない** ので、テストが失敗します。

既存のデータがある本番のDBに `NOT NULL` の列を追加するときは、既存の行に入れる値（`default`）が必要です。

## 在庫を減らす処理の注意点

- **確かめてから減らす**: 注文のすべての商品について在庫が足りることを確かめ、足りなければ何も変えずにエラーにする（トランザクション）
- **同じ商品が複数の明細にある** 場合は、合計の数量で確かめる
- 減らすときは、読んだ値から計算した値で上書きするより、`stock = stock - 数量` のようにDBの中で計算すると、同時に注文が来ても数が狂いにくい

```ts
tx.update(products).set({ stock: sql`${products.stock} - ${quantity}` }).where(eq(products.id, productId)).run();
```

## PRの説明を書く

総まとめの課題は、変更が大きくなります。レビューする人のために、PRの説明に次を書きましょう。

- 何を作ったか（仕様書のどこに対応するか）
- 設計で判断したこと（どこに何を置いたか、なぜそうしたか）
- 確かめたこと（テスト、画面での確認）
- 対象外にしたこと、気になっていること
